# 실험 기록: 무엇을 어떻게 확인했나

최종보고서와 이후 작업에서 한 실험을 실험 단위로 정리한다. 실험마다 방법, 확인된 사실, 확인하지 못한 것, 근거 위치만 적는다. 수식과 계산 과정은 [상세 해설](report-detail/README.md)에 있다.

실험마다 자료, 판정 단위, 분모가 다르므로 수치를 하나의 정확도로 합치지 않는다.

## 1. 정상 팬 실측

**방법.** ESP32 DevKitC V4, ADXL345, 12 V 직류 팬의 FG 출력으로 정상 운전 중 진동과 회전수를 함께 기록했다. 512표본 창의 FFT에서 진동 1× 주파수를 구하고, FG 펄스 주파수를 PPR 2로 환산한 회전수와 비교했다. 두 번째 운전 구간 339행에서 기동 직후 3행을 뺀 정속 구간 336행(393.19~957.33초)을 분석했다.

**확인된 사실.**

| 항목 | 결과 |
|---|---|
| 기록 샘플링 주파수 | 400.52 Hz |
| FG 평균 펄스 주파수 | 137.15 Hz |
| 진동 1× 평균 주파수 | 68.07 Hz |
| 회전수 상대오차 3% 이내 | 333/336행, 99.1% |
| 회전수 상대오차 2% 이내 | 307/336행, 91.4% |

센서 취득과 FG 회전 기준이 서로 대응한다는 것을 보여 준다.

**확인하지 못한 것.** 고장을 만든 상태의 팬은 측정하지 않았다. 따라서 이 실험으로 고장 탐지 성능은 알 수 없다. 부하, 센서 부착 위치, 운전 조건은 정상 기준에 저장되지 않으므로 조건이 바뀌면 기준을 다시 등록해야 한다.

**근거.** 보고서 Ⅳ-4, 표 12, 출처 [11]. 원 기록 `test_steaystate_baseline10min.txt`는 저장소 밖에 있다. 계산은 [FG와 하드웨어](report-detail/05-fg-hardware.md).

## 2. 고장 유형 분류 모델 개발 평가

**방법.** 공개 자료 Mendeley Mechanical faults(Version 3)의 정상, 불평형, 축 정렬 불량, 기계적 이완 네 상태를 사용했다. 20개 재조립 회차의 1,200기록을 회차별로 나눈 5분할 교차검증으로 평가했다. 같은 회차의 기록이 학습과 시험에 섞이지 않게 하기 위해서다. 입력은 선택한 한 축의 1초 구간(400 Hz, 400표본)이고 101개 특징을 계산한다.

**확인된 사실.** 전체 정확도 93.67%, 축 정렬 불량 검출률 86.00%, 기계적 이완 검출률 88.67%.

**확인하지 못한 것.** 이 수치는 모델을 고르는 과정에서 쓴 개발 평가다. 장치에 넣은 구현은 다섯 분할 모델의 점수를 평균하는데, 이 평균 모델 자체의 성능과 실제 ADXL345 입력에서의 성능은 평가하지 않았다(`ensemble_evaluated=false`, `live_validated=false`). 벨트 느슨함과 베어링 결함은 이 모델의 분류 대상이 아니다.

**근거.** 보고서 표 1, Ⅲ-3. 특징과 모델은 [학습 모델과 101특징](report-detail/03-ml-model.md), 코드는 [`ml/report_model/`](../ml/report_model/)과 [`edge_module_c/report_ml/`](../edge_module_c/report_ml/).

## 3. CWRU 베어링 잠금 시험

**방법.** CWRU 공개 파형에서 정상 1개와 내륜, 외륜, 볼 결함 각 3개, 총 10개 파일을 사용했다. 이 파일들은 모델과 임계값을 고를 때 쓴 자료와 분리했다. 단일 채널 12 kHz 신호를 4,096표본 창으로 자르고 2,048표본씩 이동했다. 분류 결과에 4/5 확인 규칙(최근 5창 중 4창 이상)을 적용했고, 파일마다 처음 4창은 확인 버퍼로 써서 전체 640창 중 600창을 평가했다. 펌웨어의 C 입력 경로에 같은 원신호를 넣어 PC에서 재생했다.

**확인된 사실.**

- 4/5 적용 후 결함 486/486창 탐지, 정상 114창의 확정 오경보 0건.
- 정상, 볼, 내륜, 외륜을 가르는 세부 분류는 640창 중 581창 정답(90.78%).
- C 구현과 Python 구현의 분류 결과가 640창 모두에서 일치. 특징값 최대 차이 2.98×10⁻¹³, 점수 최대 차이 4.33×10⁻¹³.
- 이 경로를 포함한 v1.8 ESP32 펌웨어의 빌드 성공.

**확인하지 못한 것.** PC 재생과 빌드까지 확인했다. 실제 12 kHz 센서를 장치에 달아 측정한 결과는 없다. 현재 ADXL345 400 Hz 입력으로는 베어링 결함을 관측할 수 없다.

**근거.** 보고서 Ⅳ-1, Ⅳ-3, 표 9, 표 11, 출처 [13]. 결과 파일은 [`report_cwru/verification/result.json`](../edge_module_c/report_cwru/verification/result.json).

## 4. AI-Hub 재생 평가

**방법.** AI-Hub 공개 자료의 4 kHz 원자료를 1 kHz로 재표본화했다. 설비 그룹별 정상 120창으로 기준을 만들고 C 연산 모듈(V2)로 판정했다. 순간 이상 후보의 기준은 |z| > 3이다. 결과는 파일 단위로, 파일의 마지막 판정을 집계했다. 탐지율과 오경보율의 분모는 판정 가능한 파일이고, 판정 가능 비율의 분모는 전체 파일이다.

**확인된 사실.**

| 결함 | 판정 가능한 파일 중 탐지 | 전체 파일 중 판정 가능 | 전체 파일 대비 탐지 |
|---|---|---|---|
| 베어링 | 20,547/20,547 = 100% | 20,547/25,060 = 81.99% | 81.99% |
| 축 정렬 불량 | 8,534/9,108 = 93.70% | 9,108/22,795 = 39.96% | 37.44% |
| 벨트 느슨함 | 10,218/11,677 = 87.51% | 11,677/16,343 = 71.45% | 62.52% |

벨트 느슨함의 정상 오경보는 538/9,283파일(5.80%)이다.

**판정 규칙 비교.** 벨트 자료에 기존 4/5 규칙과 20창 반복 확인 규칙을 둘 다 적용했다. 두 규칙의 임계값은 실행 전에 고정했다.

| 지표 | 기존 4/5 | 20창 반복 확인 |
|---|---|---|
| 판정 가능한 결함 파일의 탐지율 | 87.51% | 90.60% |
| 전체 결함 파일 대비 탐지 비율 | 62.52% | 59.90% |
| 정상 오경보율 | 5.80% | 11.31% |

20창 규칙은 판정 가능한 파일 안에서는 탐지율이 높지만, 판정 가능한 파일 자체가 871개 줄고 오경보가 늘었다. 그래서 4/5 규칙을 유지했다.

**확인하지 못한 것.**

- 이 자료는 설계 과정에서 쓴 개발 검증 자료다. 분리해 둔 시험 자료가 아니다.
- 축 정렬 불량은 7개 설비 그룹 중 2개에서 판정 가능한 파일이 0개였고, 1개 그룹에서는 판정 가능한 318파일의 탐지가 0건이었다.
- 베어링과 축 정렬 불량은 결함 파일만 집계해서 정상 오경보율이 없다.
- 여기서 쓴 V2 판정기는 현재 장치의 두 분석 경로와 다른 판정기다.

**근거.** 보고서 Ⅳ-1, Ⅳ-2, 표 9, 표 10, 출처 [5][6][7]. 분자와 분모는 [결과와 검증 범위](report-detail/06-results.md). 원 산출물 JSON은 저장소 밖에 있다([출처](report-detail/08-sources.md)).

## 5. B02~B04 베어링 열화

**방법.** 각 기록의 처음 10%에서 AC RMS의 99분위수를 임계값으로 정했다. 그다음 10%를 정상, 마지막 10%를 열화로 지정했다. 두 수평 채널에 각각 4/5 확인 규칙을 적용했다. 평가 단위는 1.6초 취득 구간이다.

**확인된 사실.** 채널별 평가 가능한 522개 취득 구간(전체 546개)에서 초기 261개는 모두 정상, 말기 261개는 모두 열화로 판정했다.

**확인하지 못한 것.** 정상과 열화 라벨은 기록 시각으로 붙인 대리 라벨이다. 그 시점에 실제로 고장이 있었는지 확인한 것이 아니다. B01은 기록 종료 시각과 운영 기록이 달라 제외했다.

**근거.** 보고서 Ⅳ-1, 표 9, 출처 [5][6].

## 6. 소프트웨어 이식과 펌웨어 빌드

**방법.** Python으로 정의한 판정 정책과 신호 계산을 C로 옮긴 뒤, 같은 입력을 양쪽에 넣어 결과를 비교했다. C 신호 모듈은 합성 신호로 검사했고 ESP32용 펌웨어를 PlatformIO(`esp32dev`)로 빌드했다. 검증일은 9월 26일과 10월 1~2일이다.

**확인된 사실.**

| 대상 | 결과 |
|---|---|
| Python/C 판정 정책 | 219회 갱신에서 상태와 투표 결과 일치. 초기화, 부분 수집, 임계값 경계, 비정상 숫자 입력 검사 통과 |
| C 신호 모듈 | 합성 신호의 1× 진폭 0.12 g, 0.07 g과 위상 복원. PPR 2, 3, 8과 입력 오류 처리 검사 통과 |
| Python 회귀 검사 | 36개 테스트와 23개 하위 검사 통과 |
| FG V3 펌웨어 빌드 | 성공. 정적 RAM 100,380 B(30.6%), Flash 320,561 B(24.5%) |
| CWRU 통합 펌웨어 빌드 | 성공. 정적 RAM 105,308 B, Flash 375,349 B |

**확인하지 못한 것.** 계산이 서로 일치한다는 것과 장치에 올릴 수 있는 크기라는 것을 확인했다. 실행 중 메모리 사용량, 처리 시간, 데이터 누락은 측정하지 않았다.

**근거.** 보고서 Ⅳ-3, 표 11, 출처 [8][13]. 검증한 소스 사본은 [`source_snapshot/`](../edge_module_c/esp32/edge_alimi_adxl345_fg_report/source_snapshot/).

## 7. 보고서 이후 개선 (`postreport_v2`)

보고서 제출 뒤에 추가한 작업이다. 위 1~6의 결과는 이 버전을 검증한 것이 아니다.

**방법.** 측정 기록을 수신 상태, 취득창 품질, 창 사이 공백으로 나눠 기록하도록 바꿨다. 정상 기준은 후보로 저장한 뒤 명시적으로 승인해야 운영에 쓰이게 했다. PC에서 모의 입력으로 검사하고 ESP32 빌드를 확인했다.

**확인된 사실.** PC 검사에서 후보 생성·승인·복원, 저장 실패와 손상 처리, 구형 로그 호환, 화면 표시가 통과했다. ESP32 빌드와 설치 패키지의 해시를 확인했다.

**확인하지 못한 것.** 장치 업로드, 실제 센서 입력, 전원 중단, 장기 운전, 고장 탐지 성능은 아직 검증하지 않았다.

**근거.** [후속 개선 기록](post-report-improvements.md), [측정 품질](measurement-quality.md), [정상 기준 관리](baseline-lifecycle.md), [설치 준비](firmware-installation.md).

## 보고서 결과 표에 없는 평가

Epson Rotor Kit 불평형 1× 평가는 출처 [5][6]에 기록이 있으나 보고서의 결과 표에는 수치가 없다. 이 문서에도 수치를 적지 않는다.
